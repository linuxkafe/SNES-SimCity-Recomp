## Retraction of framing

**The brief's leading claim is refuted: `$018907` DOES return — the run completes 3400 frames.** What is true, and measured, is narrower: `$018907` is entered once at f3340 and control **never reaches `$00:80B1`** (the `RTS` that was supposed to follow the `JSL`). The difference matters: "never returns" implied a hang; the measurement shows a diversion.

## 3. The decisive question: spinning, blocked, or trapped?

**Measured: neither.** The run completes 3400 frames with `EXIT=0`. `master_clock` and `insns` advance every frame. The vblank token `$00C7` advances 5/5. This is not a hang.

What IS measured:

| observation | value |
|---|---|
| distinct PCs in `$018907`'s prologue (`$018907`–`$018925`) | 1 execution each |
| PCs in the 1024-iter loop `$01F1E4`/`$01F1E8`/`$01F1E9`/`$01F1EA` | **1024 each** — finite, not infinite |
| PC `$01F1DC` (the `JSR` target) | 1 |
| PC `$01F1EC` (post-loop) | 1 |
| PCs in `$01DF7B`–`$01DF85` (NMI-disable + JSL dispatch) | 1 each |
| PCs in `$008206`–`$00821E` (COP handler setup + dispatch) | present |
| PCs in vblank wait `$00930D`–`$009315` | 2887 iterations per frame |
| PCs in NMI handler `$0080B2`–`$0080BF` | present at frame boundaries |
| **PC `$0080B1` (`RTS`)** | **0 in 1 732 639 `[itb]` lines (f3250–f3400)** |

The routine is **not spinning** (the 1024-iter loop exits), **not blocked** (the run completes), **not trapped** (no unimplemented opcode path observed). It runs and the host continues advancing frames.

**What it IS doing:** `$018907` is a **one-shot city-creation initialiser** that sets up HDMA, zeroes state, calls subroutines, and then hands control to a path that **bypasses `$00:80B1` entirely**. The code after the 1024-iter loop calls `$01DF7B`, which:

1. `SEP #$30 / SEP #$20` — sets M=1, X=1
2. `LDA $B3 / AND #$7F / STA $B1` — **clears bit 7 of `$00B1`**, which disables the NMI's long (frame-work) path and forces the short path (`INC $B9 / PLA / RTI`)
3. `JSL $008206` — calls a subroutine that dispatches a COP `#0` to the vblank wait (`$930D`)
4. After the vblank wait returns, sets OAM/HDMA registers (`$2116`, `$2117`, `$4300`–`$4306`)
5. Loops 16 times doing HDMA setup, then `RTS` to `$018931`

After that, the code runs `CLI`, calls `$C8B7` and `$C817`, then does two COP `#0` dispatches (each running the vblank wait), then enters the debug poll loop at `$018955`–`$01897A` that checks `$011B`.

**The NMI fires during this sequence** (the vblank wait can't exit without the NMI setting `$B9`), takes the short path, and returns. The vblank wait then exits, control flows back through `$008206`'s RTL to `$01DF8A`, then through the HDMA setup loop, then RTS to `$018931`. But `$0080B1` is **never reached** — the code after `$018931` (`CLI`, `JSR $C8B7`, `JSR $C817`, etc.) either executes so fast that the 1-in-8 sampling misses it, or it branches into a path that never falls through to `$80B1`.

**Verdict R2:** **neither spinning nor blocked nor trapped** — the run completes. The "never returns" in the brief meant "never returns to `$00:80B1`", not "hangs the emulation".

## 4. Stack-accounting falsifier (R1)

The brief stated `S` moved `1FFD` → `1FF8` = 5 bytes. **My measurement disagrees.**

| source | frame | site | `S=` |
|---|---|---|---|
| T113 `$00B1` write-watch | f3338 | `$00:8098` | `1FFD` |
| **T114 `$00AF` write-watch** | **f3340** | **`$01:890A`** | **`1FFA`** |

My measurement shows **`1FFD` → `1FFA` = 3 bytes**, not 5. The JSL at `$80AD` pushes 4 bytes (P + 3-byte return address). Between f3338 and f3340 the code runs two COP dispatches (`$809F`, `$80A6`); each COP handler does `PHB` (+1) + `PEA $0000` (+2) + `PLB` (-1) + `PLB` (-1) + `JSR` (+2) + `PLB` (-1) + `RTI` (-3) = **net -1 per dispatch**. Two dispatches = -2. Then JSL = -4. Total expected: `-6`. Observed: `-3`.

**R1: not established.** I cannot account for all 5 bytes because the measurement shows only 3 bytes of movement. The discrepancy is **OPEN** — there may be additional stack operations (PHA/PLA inside the COP dispatch targets or inside the vblank-wait path) that I did not instrument. I do not guess at the missing 2 bytes.

## 5. `$00AF` — whether S is restored (R4)

**Measured: S is NOT restored inside `$018907`.** `$00AF` is written exactly once during `$018907`'s execution (f3340, `IPC=01890A`). No subsequent write to `$00AF` appears in the full 3400-frame trace. Since `$00AF` is only written by `$018907`'s `STX $AF`, the absence of further writes means `$018907` either never executes another `TSX` or never writes to `$AF` again — in either case, **S is not captured being restored**.

**R4: S is NOT restored (or at least, no restoration is measured).**

## 8. What remains OPEN

1. **Why `$00:80B1` never executes.** The code path after `$80AD JSL $018907` is established (trace proves it), but the exact instruction that diverts control away from `$80B1` is **not measured**. The most likely candidate is the `BEQ $894D` at `$01895B` — if `$011B & $F0F0 == 0`, the branch is taken and a `BRK` trap fires at `$01894D`, which would change the execution path entirely. **This is NOT established** — I do not know whether the branch is taken or not, because those PCs (`$01895B`, `$01894D`, `$01895D`+) are not sampled in the trace.

2. **Whether `$018907` is supposed to return to `$80B1` in the reference build.** The peer comparison is unavailable. T112's census showed the peer's `$0012` is set at f2998 and bank `$03` keeps running — but we do not know whether the peer's `$00:80B1` executes or also skips.

3. **The stack-accounting gap (R1).** 3 bytes measured vs. 5 bytes claimed. The missing 2 bytes are **not established**.
