## 2. [MEASURED] What our own decoder does with `0x9C` — read from source, not from my table

`snesrecomp/runner/src/snes/interp816.c`:

```c
2003:    case 0x9c: { // stz abs
2004:      uint32_t low = 0;
2005:      uint32_t high = interp816_adrAbs(cpu, &low);
2006:      interp816_stz(cpu, low, high);
2007:      break;
2008:    }
```

```c
603: static uint32_t interp816_adrAbs(Interp816* cpu, uint32_t* low) {
604:   uint16_t adr = interp816_readOpcodeWord(cpu);     // <-- consumes 2 operand bytes
605:   *low = (cpu->db << 16) + adr;                     // <-- DB-relative. NO S TERM.
606:   return ((cpu->db << 16) + adr + 1) & 0xffffff;
607: }
```

```c
877: static void interp816_stz(Interp816* cpu, uint32_t low, uint32_t high) {
878:   if(cpu->mf) {
879:     interp816_write(cpu, low, 0);                  // M=1 -> ONE byte
880:   } else {
881:     cpu->cyclesUsed++; // m = 0: 1 extra cycle
882:     interp816_writeWord(cpu, low, high, 0, false); // M=0 -> TWO bytes
883:   }
884: }
```

Three facts fall out of the project's own code, and they are the whole answer:

1. **Length = 3.** `interp816_adrAbs` reads a 16-bit operand, so `9C` + 2 bytes.
2. **The addressing mode is absolute and DB-relative.** `low = (cpu->db << 16) + adr`.
   **`cpu->sp` does not appear.** A wrong S cannot move this store.
3. **M=0 makes it a two-byte store.** This is what the peer's two-writes-per-execution
   pattern is (§4).

### The complete set of STZ opcodes this decoder implements

Every `interp816_stz` call site, with the opcode it belongs to:

| line | opcode | mnemonic |
|---|---|---|
| 1657 | `0x64` | `stz dp` |
| 1758 | `0x74` | `stz dpx` |
| 2006 | `0x9c` | `stz abs` |
| 2018 | `0x9e` | `stz abx` |

**Four. None of them stack-relative, and `0x9C` is `abs`.** There is no `STZ $sr,S`
in this decoder to be found, because the 65816 does not have one.

**[REFUTED] the brief's "S thread", on our own source rather than on my table.**
The 65816's stack-relative block is `0x03/0x23/0x43/0x63/0x83/0xA3/0xC3/0xE3`
(`ORA/AND/EOR/ADC/STA/LDA/CMP/SBC sr,S`) and `0x13/0x33/0x53/0x73/0x93/0xB3/0xD3/0xF3`
(`… (sr,S),Y`). `STZ` is **not** in either group. Our decoder agrees, and its own
comments place `0x63` as `adc sr` — the stack-relative block, not a store.

⚠ **[NOT ESTABLISHED]** *Why* the peer's log prints `dbr=$03` alongside
`bus_addr=$030E15` and `wram_idx=$00E15`, i.e. how the peer's `sc_wram_index()`
rule maps a `$03:`-banked address into its WRAM index. The peer's
`study/peer-linux/` was **not read** for this. Not needed for any claim here and
deliberately not guessed.

- **[MEASURED] M=0, X=0 at `$03:8222`.** The node's key is `m:0, x:0`, and the node

## 8. A hypothesis of mine that the peer's log killed before I claimed it

My first reaction to `9C` was "`STZ $sr,S`, and the peer wrote `$0E15` therefore the
peer had a different S" — which would have made the brief's S thread look confirmed
and the divergence look like a stack-pointer bug. **Two log queries killed it before
it became a claim:** (a) `grep -o "IPC=..." | sort | uniq -c` on the peer shows
**two** bus writes per execution, which `STZ` can only do at M=0 and which no
stack-relative reading predicts any better than an absolute one; (b) `interp816.c`
has exactly four STZ opcodes and none is stack-relative. Recorded because it is the
same shape as the eleven measurements in this project that refuted themselves: a
plausible story surviving a log line read in isolation.
