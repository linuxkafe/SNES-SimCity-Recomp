# T102 — `$03:8026` over f3000–f13080: the answer holds, and the instrument that produced the previous answer was watching the wrong address

**Deck-native, 2026-10-03, tree `f278506`.** Four runs, 14 000 frames each, one
instrumented build and one Deck-built trace tier. **No new source code in this
project**; no peer core touched.

## The answer

**`$03:8026` executes 0 times over 14 000 frames** — with the instrument
verified live by a positive control in the same build. And alongside it, which is
what makes the zero mean anything:

| read, all in **f3000–f13080** unless stated | result |
|---|---|
| **`$03:8026` executions, whole 14 000-frame run** | **0** |
| **any bank-`$03` PC, interpreted** | **333 distinct PCs / 169 693 steps** |
| **any bank-`$03` PC, interpreted, in f3272–f13080** | **0 distinct PCs / 0 steps** |
| **any bank-`$03` AOT block entry** | **18** — 3 at f3259, 15 at f3270, **none after f3270** |
| **`$0B51`–`$0B5F` writes, whole 14 000-frame run** | **66**, every one at or before **f3259** |
| **`$0DC0`–`$0DD0` writes, whole 14 000-frame run** | **61**, in 4 events (f0, f108, f582, f3259), **none after f3259** |
| **`$0DC7`** (accumulated tax) | written **4×** (f0 `00`, f108 `1A`, f582 `00`, f3259 `00`); **never accumulated into** |
| **city-state bytes at f3300 vs f13000** | **byte-identical** |

**So the city is never *started*, not merely never *advanced*.** Bank `$03` runs
hard between f3000 and f3271 — 169 693 interpreted steps, 86% of them in four
PCs — and then executes **nothing at all** for the next **9 809 frames**, which
is the entire span in which the reference rolls its month sixteen times and
turns its year. The city-state block's last write is f3259, **10 741 frames
before the run ends.**

**And this forced a retraction (R-037).** The previous answer — T100's and
C-041c's "`0 executions over 6 000 / 9 000 frames`" — was produced by an
instrument that was **not watching `$03:8026`**. Details in §1. The conclusion
survives and is re-derived here; the measurement that produced it does not.

## 1. The falsifier fired first, and it fired on the control

T100's falsifier F1 was *"the counter prints nothing even with `PHASE_MS=1`"*.
It did not fire. The falsifier that fired was one this ticket did not have: **a
positive control on a PC that is known to execute.**

### 1.1 The control came back zero

```
$ env SNESRECOMP_COUNT_PC=009311 SNESRECOMP_PHASE_MS=1 SNESRECOMP_RUN_FRAMES=300 ...
[host +15.192s] exit: RUN_FRAMES reached after 300 frames
[count] pc watched: 0 executions over 300 frames = 0.0 per frame
```

`$00:9311` is `INC $C7`, the body of the vblank spinlock. It is the PC the
instrument **defaults** to (`interp816.c:198`, `s_interp_pc_watch = 0x009311`)
and it is the one address in this repository with the most independent evidence
that it executes: C-002 measures `$00C7` advancing 5/5, and RE_CITY_FREEZE's
WLOG census counts the spin 4 110 times in 5 000 frames. **A zero here is not a
result. It is the instrument.**

### 1.2 The cause, and it is a one-line `strtoul`

```
$ cat /tmp/oct.c && gcc -O0 -o /tmp/oct /tmp/oct.c && /tmp/oct
009311     -> strtoul(base 0) = 0 = 0x000000
038026     -> strtoul(base 0) = 3 = 0x000003
0x009311   -> strtoul(base 0) = 37649 = 0x009311
0x038026   -> strtoul(base 0) = 229414 = 0x038026
9311       -> strtoul(base 0) = 9311 = 0x00245F
00930D     -> strtoul(base 0) = 0 = 0x000000
```

`interp816.c:323` reads the knob with base **0**, which auto-detects: a leading
`0` means **octal**, and parsing stops at the first digit that is not an octal
digit. `038026` parses as `03` = **3**. `SNESRECOMP_COUNT_PC=038026` watched
**PC `$000003`**, in bank `$00`, for the whole run.

The knob is documented at `interp816.c:195` as **`SNESRECOMP_COUNT_PC=<hex>`**,
and its own default is written `0x009311` — with the prefix. The documented
usage and the documented default are both safe; the natural reading of `<hex>`
is not.

### 1.3 With the prefix, the instrument is live

```
$ env SNESRECOMP_COUNT_PC=0x009311 SNESRECOMP_PHASE_MS=1 SNESRECOMP_RUN_FRAMES=300 ...
[count] pc watched: 239617 executions over 300 frames = 798.7 per frame
$ env SNESRECOMP_COUNT_PC=0x009313 ...
[count] pc watched: 239617 executions over 300 frames = 798.7 per frame
$ env SNESRECOMP_COUNT_PC=0x038026 ...
[count] pc watched: 0 executions over 300 frames = 0.0 per frame
```

`$009311` and `$009313` agree to the unit, which is what a spin body's two
halves should do. This is also an independent confirmation of the 2026-09-30
figure in `RE_CITY_FREEZE` (`COUNT_PC=0x009311 -> 881 646` over 4 200 frames of
live city): 239 617 over 300 frames is the same order, and the two windows are
not the same window.

### 1.4 The trap was already in the record, and the next measurement walked into it

`docs/RE_CITY_FREEZE.md:1546`, dated **2026-09-30**, under the heading
*"Um bug meu que invalida probes anteriores"*:

> `interp816.c:325` usa `strtoul(e, NULL, 0)` — base 0, portanto um `0` à frente
> significa **octal**. […] **Qualquer resultado de `COUNT_PC` registado neste
> projecto sem prefixo `0x` é nulo.**

("Any `COUNT_PC` result recorded in this project without the `0x` prefix is
null.") T058 used `0x009311` and was correct. **T100 used `038026`.** The rule
was written down, in a tracked file, four days before the measurement that
violated it, and it did not protect anything — because it lived in an
append-only log at line 1546 and not in the README's instrument list, which is
the only place a reader starts. **The failure is not the parse. The failure is
that a rule in the record did not reach the next session.**

### 1.5 It is not confined to one knob

`strtol(v, NULL, 0)` / `strtoul(v, NULL, 0)` appears at **28 sites** in
`snesrecomp/runner/src` and `src/`. Three were hit in this session:

| knob | documented as | parsed with | measured symptom |
|---|---|---|---|
| `SNESRECOMP_COUNT_PC` (`interp816.c:323`) | `<hex>` | `strtoul(…, 0)` | **wrong PC watched**; silent, clean-looking zero |
| `SNESRECOMP_WRAM_DUMP_HI` (`host_main.c:1548`) | `(hex)` | `strtol(…, 0)` | `0B60` → **0**, so `hi-lo = 0`: `[wramdump] wrote … (0 bytes)` |
| `SNESRECOMP_WRAM_DUMP_LO` (`host_main.c:1547`) | `(hex)` | `strtol(…, 0)` | `0B40` → **0**, dumping the whole 128 KB instead of 32 bytes |

`SNESRECOMP_WRITE_WATCH` (`cpu_state.c:519`, `:613`) and
`SNESRECOMP_WRAM_WATCH` (`common_cpu_infra.c:937`) are documented **with** a
`0x` prefix (`0xADDR`) and are safe if the documentation is followed; they fail
the same way if it is not.

**Not fixed here, deliberately.** The fix is one character per site in a
pinned submodule, and this repository cannot ship it: `snesrecomp` is a
submodule pinned to a branch (`T097`: *submodule commit is branch-only*), so a
local edit reaches no clone and would create a divergence the tree does not
track. **What is committed instead is the rule and the retraction.**

## 2. What C-041 said, and why it is untouched

`SNESRECOMP_COUNT_PC` parses a value and compares it. `SNESRECOMP_INTERP_DUMP_BANK`
**enumerates** every distinct PC the interpreter executed in one bank. A parse
bug cannot corrupt an enumeration. So C-041 — *"`$03:8026` is not among the 921
bank-`$03` PCs"* — was never exposed to this, and neither was C-008.

Independently reconfirmed here, in the same run:

```
$ awk '/interp_dump_bank/,/ppu_split/' runA.log | grep -c '\$038026'
0
```

**C-041 stands. C-008 stands. C-041c and T100's count are retracted (R-037).**

### And the tier question is settled from the manifest, not argued

`SNESRECOMP_COUNT_PC` lives in `interp816_runOpcode`, so like `CYC_WATCH` it is
blind to the AOT tier — which is why a zero from it is a statement about the
interpreter unless something else closes the gap. Here, from
`src/gen/program_manifest.json`:

| | |
|---|---|
| nodes covering `$038026`, **all banks, all m/x modes** | **exactly 1** |
| that node | `038000:M1X1`, spanning **`$038000`–`$03815D`**, 134 instructions |
| its disposition | **`lle_only`** |
| `aot_eligible` nodes covering `$038026` | **0** |

No AOT node contains the address, and the one node that does is interpreter-only
by construction. **`SNESRECOMP_COUNT_PC=0x038026` is therefore exhaustive over
both tiers for this address**, and the zero is not a tier artefact. The AOT tier
is covered separately and independently in §4. **[MEASURED, from the manifest —
machine-independent, and it holds in a fresh clone because the manifest is
derived from the user's own ROM.]**

### 3.2 Where bank `$03`'s 169 693 steps go

```
  $03C87C         36344

```

**Four PCs are 145 371 of the 169 693 steps — 86% — and the fifth is two orders
of magnitude smaller.** ROM bytes at those addresses, read from the user's ROM
(`offset = bank*0x8000 + (addr & 0x7FFF)`, the LoROM rule of CONF-7):

| PC | ROM bytes | decode |
|---|---|---|
| `$03C877` | `9F 00 6B 7F` | `STA $7F6B00,X` (long, indexed) |
| `$03C87B` | `E8` | `INX` |
| `$03C87C` | `E0 F4` | `CPX #$F4` |
| **`$03C87F`** | `D0` | **not an instruction boundary** |

**`$03C87F` is the second byte of `8D D0 F6` = `STA $F6D0`, whose instruction
starts at `$03C87E`.** Per C-056's rule it is reported as **unattributed, not
as an executed instruction**. The three that do decode account for 109 031
steps, **64%** of the window's bank-`$03` cost.

`CPX #$F4` is followed by `STA $F6D0`, **not** by a branch, so this is a scan
loop's *test*, and its back-edge is outside the logged neighbourhood.
`STA $7F6B00,X` walking X against `$F4` is a 244-byte WRAM page. **What it is
scanning for and what ends it are NOT identified, and no cause is claimed.**
**[OPEN]**

> **The single next measurement (T104): frame-resolve the `$03C87x` scan loop —

## 8. The machine, and every caveat that travels with the number

**Every number on this page is Deck-native** (`ssh deck@steamdeck`), including
the trace tier, which was compiled on the Deck. **Host-only: none.** The two
host-side objects used here — the `strtoul` demonstration (§1.2) and the ROM
byte decode (§3.2) — are arithmetic on the C library and byte reads from the
user's own ROM, both machine-independent, and both are re-derivable in a clone.

**Environment caveat, inherited by every figure above:** the Deck's rootfs is
damaged in a way pacman does not report — 503 of the 504 `/usr/include` paths
`pacman -Ql glibc` claims are absent while the package reports installed, and
`echo '#include <stdio.h>' | gcc -E -` gives `No such file or directory`. All
builds use the hand-assembled prefix at `/home/deck/sysroot` via `-idirafter`
on **both** `CMAKE_C_FLAGS` and `CMAKE_CXX_FLAGS`. ROM md5
`23715fc7ef700b3999384d5be20f4db5`, 524 288 bytes, verified on the Deck.

**Instrument bound, stated because C-048 says it must be:** these are
instrumented builds. C-048 measured that instrumentation moves the histogram
(921 PCs / 515 043 steps plain vs 946 / 515 337 traced, same binary, same
script, same window). **Distinct-PC counts were stable across machines and runs
in that measurement; step counts were not.** So: the *counts of executions* in
§3.2 and §5 are read as instrumented-build figures, and the *structural*
findings — 0 executions of `$03:8026`, 0 bank-`$03` activity in f3272–f13080,
0 writes after f3259 — do not depend on them.

**Nothing in the reference core was touched.** No peer source is vendored,
copied or published; `study/peer-linux/` is unlicensed third-party source and
this measurement used it read-only. No change was made to it in this session.

### `exit:` discipline

All four runs were foregrounded through `ssh`, returned `EXIT=0`, and ended
`exit: RUN_FRAMES reached after 14000 frames` (439.3 s, 423.3 s, 466.6 s,
439.2 s). **No run was `timeout`-truncated and no run ended `SDL_QUIT`.** The
200/300-frame falsifier smokes also each ended `exit: RUN_FRAMES reached`.
