# Measurement — the processor status at `$03C87F` (T105, 2026-10-03)

**The question, pre-registered.** Do the flags at the two loop edges show a
**correct Z for `CPX #$F4`**? If they do, the decode hypothesis is dead and the
X the branch compares is not the X the store used — a different and more
interesting defect. If they do not, the overrun is the game failing its own
bound.

**The answer: the flags do NOT show a correct Z — and the brief's dichotomy is
refuted by the measurement itself. Neither of its two readings is right.**

The flags are wrong because **we** read the wrong operand bytes. `CPX #$F4`
consumes a **2-byte operand** in our interpreter and advances the PC by **3**,
so the word compared against is **`$8DF4`** — the bytes at `$03C87D` (`$F4`) and
`$03C87E` (`8D`) — and the loop terminates when **`X == $8DF4`**.

**This is a defect in our emulation, not in the game's code.** The
"first thing in this project that looks like a defect in the game's own code"
framing, written into `README.md` at `3f24098` **one commit earlier**, is
**RETRACTED here (R-039)**.

Deck-native throughout (`ssh deck@steamdeck`), trace tier `build-tr`,
`scripts/d_city.script`, headless. **Host-only: none.**

## 3. The flags

Distinct `P=` at `$03C87C` — the state the following `BNE` reads:

| `P=` | bits | count |
|---|---|---|
| `$04` | I | 3 571 |
| `$07` | **I Z C** | **1** |
| `$84` | N I | 32 768 |
| | **total** | **36 340** |

`xf = 0` throughout (bit 4 clear in every row), so X is 16-bit.

**The one iteration where Z is set:**

```
[cyc] f=3270 pc=$03C87C op=$E0 P=$07 A=0000 X=8DF4 Y=0000 SP=1FF6 D=0000 DB=03 NPC=03C87F
```

**And the one iteration where the bound says it should be:**

```
[cyc] f=3259 pc=$03C87C op=$E0 P=$04 A=0000 X=00F4 Y=0000 SP=1FF6 D=0000 DB=03 NPC=03C87F
```

`P=$04` → **Z clear** at `X == $00F4`. **The loop sails past its own bound
because the compare does not fire there.**

The single exit is the same single row, seen from the branch:

```
[cyc] f=3270 pc=$03C87F op=$D0 P=$07 A=0000 X=8DF4 ... NPC=03C881
```

`NPC=03C881` × **1**, `NPC=03C877` × **36 339** — T104's taken/not-taken split,
reproduced to the unit, now explained: **Z is set exactly once, at `X=$8DF4`.**

## 4. The operand is `$8DF4` — three independent confirmations

**(a) The next PC.** `NPC` produced by `$03C87C`, over all 36 340 iterations:

```
36340 NPC=03C87F
```

**One** value. `E0 F4` is a 2-byte instruction; we advance by **3**. That is why
`$03C87E` never executes — and it is the whole of T104's skip anomaly.

**(b) The terminal value.** Z is set at `X=$8DF4`, and the arithmetic is exact:
comparing X against `$8DF4` gives `X − $8DF4`, which is **0 only at
`X=$8DF4`**, and sets both **Z and C** — measured `P=$07`, i.e. Z=1 **and** C=1,
the only row with C set. Comparing against `$00F4` would set Z at `X=$00F4`,
which is a *different iteration* and had `P=$04`.

**(c) The N-flag census — the strongest of the three, because it is a
prediction over all 36 340 rows rather than one.** If the operand is `$8DF4`
then the implementation computes `X + ~$8DF4 + 1 = X + $720C`, so **N is set iff
`X + $720C ≥ $8000`, i.e. iff `X ≥ $0DF4`.** That predicts exactly **3 572**
iterations with N clear and **32 768** with N set. **Measured: 3 572 and
32 768.** No other operand value reproduces both numbers.

```
0x0DF4 = 3572 ; expected N clear = 3572
observed N clear = 3572  ; observed N set = 32768
```

**X over the whole loop**, from the 36 340 rows at the loop head:

| | |
|---|---|
| rows | 36 340 |
| **distinct X values** | **36 340** |
| first / last | `$0000` / `$8DF3` |
| `sort -c` non-decreasing | **YES** — no repeats, no reversals |

So the loop ran `X = $0000 → $8DF3`, strictly monotonic, and stopped on the
compare at `$8DF4`. **This also corrects T104's §9** — it recorded the extent
as *"X was followed to `$14FF`. Above that, nothing was watched"*, which was an
**instrument limit** (`WLOG_ADDR` watched a 16-bit range, `$6B00–$7FFF`), not a
property of the loop. The loop reaches `$8DF3`.

## 5. The differential, from the same log: `LDA #imm` is correct

The opcode fetch advances the PC by one before `doOpcode` runs
(`runOpcode`: `uint8_t opcode = interp816_readOpcode(cpu);`, and
`readOpcode` is `cpu->read(cpu->mem, (k<<16) | cpu->pc++)`). The immediate helper
then advances it again, once or twice, on the width flag.

Both classes were observed **in this one run**:

| instruction | bytes | m / x | operand read | PC advance | correct? |
|---|---|---|---|---|---|
| `$03C871 LDA #$0000` | `A9 00 00` | m=1 | `$0000` | 3 | **yes** — measured `A=$0000` on all 36 340 rows at `$03C877`. A one-byte overread would give `$00A2`, the next byte in ROM (`A2` = `LDX` at `$03C874`) |
| `$03C87C CPX #$F4` | `E0 F4` | x=0 | **`$8DF4`** | **3** | **no** — 2 required |

**An instrument that reads one register file correctly and another wrongly in
the same 36 340 rows is proven live.** That is F5, and it is also the
localisation: the defect is not "the flags are broken", it is **the
index-width immediate path**.

**Which opcodes are affected** — from the dispatch, the `xFlag=true` call sites
of `interp816_adrImm` are exactly four:

```
interp816.c:2029  case 0xa0  ldy imm(x)
interp816.c:2041  case 0xa2  ldx imm(x)
interp816.c:2228  case 0xc0  cpy imm(x)
interp816.c:2419  case 0xe0  cpx imm(x)
```

**`$A0 $A2 $C0 $E0` — and only while `xf = 0`.** With `xf = 1` the helper takes
its 1-byte branch and is correct. `$03C874 LDX #$0000` (`A2 00 00`, 3 bytes) runs
correctly in the same loop, which is consistent: `A2` is only broken in the case
that does not arise here.

> **The 65816 rule these four violate** — on the 65816 the immediate operand of
> `LDX`/`LDY`/`CPX`/`CPY #imm` is **8 bits, always**. Only the accumulator/ALU
> group (`LDA`/`ORA`/`AND`/`EOR`/`ADC`/`SBC`/`CMP`/`BIT`) follows the **m** flag
> for immediate width. The x flag governs *index register* width, not the width
> of these four opcodes' operand.
> **Stated as [INFERRED], not [MEASURED].** This repository contains no
> independent 65816 length authority to check it against (§6), and the brief's
> standing rule — *do not use your own length table as evidence* — applies to
> this sentence as much as to any other.
>
> **The finding does not depend on it.** What is measured is that *our*
> interpreter reads two operand bytes for `$E0` and advances three, and that the
> resulting terminal value is `$8DF4`. Whether hardware takes one byte or two
> changes the fix; it does not change the measurement.
>
> **One piece of internal corroboration, offered as corroboration and not as
> proof:** under the 1-byte reading the bound is `$00F4` and the loop is a
> 245-iteration clear, which is a sane thing for a program to do. Under the
> 2-byte reading the bound is `$8DF4` and the loop clears 36 340 bytes of WRAM,
> which is not a thing anyone writes on purpose. A bound that is meaningless is
> evidence about the reading.

## 6. Why the project's own tests never saw this — CONF-21

The submodule's accuracy report
(`snesrecomp/SNES_ACCURACY_BURNDOWN.md:108`) records **"533 opcode variants,
0 divergences (1.599M checks)"** against `interp816`.

**Those checks compare the AOT code generator against `interp816`.** They are an
internal-consistency suite, not a conformance suite. And the corpus generator
encodes the same wrong assumption as the interpreter, so the operand bytes it
plants are wrong too:

```
snesrecomp/tests/cpu_diff/gen_ops.py:30
  # index-immediate compares/loads (width = X flag)
  IMMX_OPS = [("ldx", 0xA2), ("ldy", 0xA0), ("cpx", 0xE0), ("cpy", 0xC0)]
  ...
  gen_ops.py:67
        emit(f"{label}_{imm:02x}_lo_x0", [op, imm, 0x00], 1, 0)   # 16-bit index
```

Line 30's comment **is the defect, restated as a test-corpus invariant**, and
line 67 emits `[op, imm, 0x00]` — a 3-byte encoding — for the `x=0` case. The
interpreter and the corpus therefore agree, and **agreement between them cannot
detect it.** 1.599M checks, zero divergences, and a defect.

**This is the project's own recurring lesson in its purest form, one level
down:** an instrument that cannot see the answer looks exactly like an
instrument that found nothing. Filed as `docs/CONFLICTS.md` **CONF-21**. **Not
fixed here** — it lives in a submodule and the fix requires an external
conformance reference this repository does not have.

## 7. What this does NOT establish

- **It is not a cause for the freeze, and it does not explain why the city does
  not simulate.** C-006 stays **OPEN**. Nothing here touches `$03:8026`, the
  `$0012` gate, or the abandoned city-state block.
- **It does not say the loop *should* clear 245 bytes.** That is the natural
  reading of a `$00F4` bound and it is an **[INFERRED]** consequence, not a
  measurement. Whether `$7F6B00`+245 bytes is the intended target is unexamined.
- **It does not quantify the fallout.** The loop wrote `$00` to
  `$7F6B00 + X` for `X = $0000…$8DF3`, i.e. **~36 KB of WRAM** (the low mirror
  region `$6B00`–`$F8F3`), over f3259–f3270. **What that destroyed is not
  measured**, and no claim is made about it. **This is the most important thing
  left open** and it is the obvious next measurement (§9).
- **It does not establish the size of the blast radius across the game.** That
  `$A0/$A2/$C0/$E0` are affected *while `xf=0`* is from the dispatch, not from a
  census of how often that is true in this ROM.
- **Step counts remain instrumented-build figures** (C-048/C-049). The
  *structural* results — `NPC=03C87F` ×36 340, Z set once, at `$8DF4`, `P` taking
  3 values — are zero-vs-nonzero and do not depend on them.
- **The reference implementation was not consulted.** `study/peer-linux/` was
  not read and no third-party emulator source was used.
- **`make perf` is not run in this document**; see the commit body.

## 8. The retraction this measurement forces — R-039

`README.md` at **`3f24098`**, one commit before this run, said:

> *"This is the first thing in this project that looks like a **defect in the
> game's own code** rather than in our emulation."* … *"There are **two**
> readings and **nothing here distinguishes them**: the game's own bug … or a
> wrong register state on our side … **It is NOT established which.**"*

**Refuted.** It is the second one, and it is not merely "a wrong register state"
— it is a wrong **operand fetch** in our interpreter, with the register file,
the flags machinery and the branch all behaving correctly on the input they were
given.

**The error was mine and it is the brief's error too.** The brief's Step 2
framed the outcome as *"If they do not, the overrun is the game genuinely
failing its own bound and we have found a game bug."* **That inference does not
follow.** The flags are computed by *our* emulator from *our* operand fetch; a
wrong Z is evidence about us, not about the game, and this run contains the
control that separates them (§5: `LDA #imm` correct, `CPX #imm` wrong, same log,
same instrument).

**And note the direction of the error.** Three sessions framed this loop as a
mystery in the game's code. Every one of the anomalies in it — the skipped
byte, the missing Z, the 2 069 stores past the bound, the 36 KB written — is one
defect on our side.

## 9. The single next measurement

**Fix nothing yet. First measure what the overrun destroyed, because fixing the
decode will make the loop run ~8 500× longer, not shorter.**

The terminal value moves from `$8DF4` (36 340 iterations, bounded) to `$00F4`
(245 iterations) *if* the game meant `$00F4` — and **if it meant something else,
or if the loop's real exit is elsewhere, a corrected decode leaves it
unbounded.** Either way the corrected decode is a *bigger* write than the
buggy one, and the safe order is:

1. **Census `$A0/$A2/$C0/$E0` in this ROM under `xf=0`** — how many executions,
   at which PCs, in which frames. This is the blast radius, and it is the same
   shape as the T104 run: `COUNT_PC` per opcode plus `INTERP_DUMP_BANK`. It is
   cheap and it bounds how much of the rest of the register is affected.
2. **Then** fix the width, on the strength of §5, and re-run T104's loop census.
   The predicted post-fix shape is a 245-iteration loop terminating with a
   correct `Z`/`C` at `X=$00F4`, and **that prediction is falsifiable in one
   run** — which makes it a proper acceptance test rather than a hope.
3. **Only then** ask whether the loop terminating correctly makes the city
   simulate. It is a **diagnostic, not a fix**: if it does, the loop was a
   gate, and that is a different and larger finding. **No cause is claimed
   until that is measured**, and **`make clock` must stay red** regardless —
   DoD Rule 0.
