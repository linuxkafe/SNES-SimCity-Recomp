# Measurement — what gates the entry into bank `$03` (2026-10-02)

**The question.** C-039b measured *where* bank `$03`'s execution stops — f3271,
78 frames before the city appears. Phase 4 asks the other half: **what gates the
entry**, not what the callee does.

**The answer, in one sentence.** Bank `$03` is entered by a **flag test at
`$00:804D`**, it is **resumed by `RTI` rather than called**, and the flag
(`$0012`) is set to 1 **by bank `$03` itself, one instruction before it returns
for the last time** — so the gate is closed before the code that would read it
ever comes back.

All numbers below are **DECK-NATIVE**: `steamdeck`, gcc 15.1.1, Zen 2, the
`build-instr` tier rebuilt from the current tree, `scripts/d_city.script`,
headless. The host is used only for ROM byte reads, which are machine-independent
and cross-checked against the measured PC lengths.

## 1. The gate, read from ROM bytes

`$00:8040`–`$00:8060` (file `0x0040`–`0x0060`), decoded:

```
$00:8040  20 EE 25 0B   JSR $0B25EE
$00:8044  A9 81        LDA #$0081
$00:8046  85 B3        STA $B3
$00:8048  85 B1        STA $B1
$00:804A  8D 00 42     STA $4200
$00:804D  A5 12        LDA $0012        <-- loop head, THE GATE
$00:804F  D0 0B        BNE $805C        <-- $0012 != 0  ->  bank 03 skipped
$00:8051  64 B7        STZ $B7
$00:8053  20 65 8D     JSR $8D65
$00:8056  22 83 D2 03  JSL $03D283      <-- BANK $03 ENTRY
$00:805A  80 F1        BRA $804D
$00:805C  20 61 80     JSR $8061        <-- the other path
$00:805F  80 80        BRA $8040
```

## 2. The gate is read twice in 3700 frames, and the bank-`$03` entry is taken once

`SNESRECOMP_COUNT_PC` (see §6 — it has a trap), whole run, 3700 frames:

```
[count] pc watched: 2 executions over 3700 frames   # $00:804D  LDA $0012
[count] pc watched: 1 executions over 3700 frames   # $00:8056  JSL $03D283
[count] pc watched: 1 executions over 3700 frames   # $03:D2AA  STA $0012
```

So this is **not** a per-frame loop. The gate is tested **twice** in the whole
run, and the bank-`$03` entry is taken **once**.

## 3. What closes the gate

`SNESRECOMP_WLOG_ADDR="0012:0012:…" SNESRECOMP_WLOG_STATE=1`, whole run:
**`$0012` has exactly three writes in 3700 frames.**

```
frame  bank:addr  value  writer
f0      00:0012    00     interp@$008023  A=0000 DB=00
f108    7F:0012    E0     interp@$059304  A=7FED DB=7F
f3271   00:0012    01     interp@$009311  A=0001 DB=03  IPC=$03D2AA
```

**The third is the one.** It is at **f3271** — the frame bank `$03` dies on — and
the writing PC is **`$03:D2AA`**, inside bank `$03`. ROM bytes at `0x1D2AA`:

```
$03:D2A7  A9 01 00   LDA #$0001
$03:D2AA  85 12      STA $0012       <-- the gate flag, set to 1
$03:D2AC  E2 20      SEP #$20
$03:D2AE  A9 FF      LDA #$00FF
$03:D2B0  8D 2A 0B   STA $0B2A
$03:D2B3  A9 00      LDA #$0000
$03:D2B5  48         PHA
$03:D2B6  AB         PLB
$03:D2B7  6B         RTL
```

`$03:D2AA` is the **15th of 16 instructions** bank `$03` ever executes in f3271,
and `RTL` at `$03:D2B7` is the last. The routine opens its own gate on its way
out. The logged `A=0001` and the logged value `01` agree with the `LDA #$0001`
two bytes earlier — the write, the bank, the frame and the ROM bytes all agree.

### The ordering is the whole finding

Per-frame execution order in f3271 (`SNESRECOMP_INTERP_TRACE_FRAMES=3265-3275`):

| instruction | executions in f3265–f3275 |
|---|---|
| `$00:804D` `LDA $0012` | **1** (f3271) |
| `$00:804F` `BNE $805C` | 1 (f3271) |
| `$00:8051` / `$00:8053` (the `$0012 == 0` path) | **0** |
| `$00:8056` `JSL $03D283` | **0** |
| `$00:805C` `JSR $8061` | 1 (f3271) |
| `$00:805A` `BRA $804D` | 1 (f3271) |
| bank-`$03` PCs, f3272–f3275 | **0** |

So, in f3271, in this order:

1. bank `$03` reaches `$03:D2AA` and sets `$0012 = 1`;
2. `RTL` at `$03:D2B7` returns to bank `$00`;
3. bank `$00` reaches `$00:804D` — reads `$0012 = 1` — takes `BNE` — goes to
   `$00:8061` instead of `$00:8056`;
4. **`$00:804D` is never executed again in the run.**

The gate was closed *before* its only two readings were resolved, and the reader
never came back to find out. After f3271: **zero** interpreted bank-`$03` steps
and **zero** AOT bank-`$03` entries, through f3700 (both tiers, Deck-native).

## 4. Bank `$03` is resumed by `RTI`, not called — C-050 promoted

C-050 was **INFERRED**: "*the bank-03 task region is entered by `RTI`, not by a
call* — `$00:8222` = `40 0D 93` = `RTI` immediately precedes `$03D299` in the
stream … **no stack was dumped**."

It is now **MEASURED**, twice over.

**(a) The execution order.** Transitions into and out of bank `$03` in
f1201–f1203, classified by the predecessor/successor PC:

```
INTO   bank $03:   12 x from $008222      (RTI)
                    3 x from $059BA0
OUT of bank $03:   12 x to   $008211
                    3 x to   $059B94
```

A full cycle, in execution order, straight from the trace:

```
$03DBB3         bank 03 code
$008211  58
$008212  8B     PHB
$008213  F4 00  PHD
$008216  AB     PLB
$008217  AB     PLB
$008218  C2 20  REP #$20
$00821A  C2 10  REP #$10
$00821C  0A     ASL A
$00821D  AA     TAX
$00821E  FC 23 82   JSR ($8223,X)     <-- handler table, indexed by A
$008221  AB     PLB
$008222  40     RTI
$03DBB5         <-- back inside bank $03
```

and the NMI path through the same epilogue:

```
$009311 $009313 $009315 $009317   the NMI handler $00:930D..$9317, ends RTS
$008221  AB     PLB
$008222  40     RTI
$03D299         <-- bank $03 again
```

**(b) The code.** `$00:8211`–`$00:8223` from ROM is a dispatcher: save
data/stack banks, `ASL A` / `TAX`, `JSR ($8223,X)` through a handler table,
`PLB`, `RTI`. The table at `$00:8223` contains `$930D` **twice** (at X=`$08` and
X=`$0A`) — and `$930D` is the NMI handler. So both IRQ and NMI run through this
one entry, and `RTI` is what puts the CPU back where it was.

**This is why "what calls into bank 03" is the wrong question.** Nothing calls it
recursively in the way a caller/callee census would find: control arrives by
`RTI` restoring an interrupted context. The stack was not needed to see this; the
transition census and the ROM code see it.

## 5. ONE THING NOT RECONCILED — recorded, not smoothed over

The instruction at **`$03:DBB3`**, which the trace shows transferring control to
`$00:8211`, **does not read as a transfer to `$00:8211`.** ROM bytes at
`0x1DBB3` are **`02 00 60`** = `JMP $036000`. And **`$03:6000` never executes** —
`pc=$036xxx` appears **0 times** in the f1201–f1203 trace. A search of bank `$03`
for `22 11 82 00` (`JSL $008211`) and `02 11 82` (`JMP $008211`) returns
nothing.

So one of three things is wrong, and **I did not determine which**:

- the ROM read or the LoROM mapping at this address, or
- the `[itb]` PC attribution for this one step, or
- the intervening instruction is not `[itb]`-visible (AOT boundary, or an
  interrupt taken between two logged steps — an IRQ taken while PC=`$03DBB3`
  would push `$03DBB5`, which is exactly where `RTI` lands, and `$03DBB5` = `60`
  = `RTS`).

The third is the most likely and it is consistent with §4: **bank `$03` raises an
IRQ.** But "most likely and consistent" is not a measurement, so it is written
here as **OPEN**, and no claim above depends on it. Everything in §1–§4 rests on
ROM bytes and on logged PC sequences, not on this instruction.

## 6. A sixth instrument trap: `COUNT_PC` prints nothing

`SNESRECOMP_COUNT_PC=<hex>` counts executions of one 24-bit PC and the counter
works — but the only `fprintf` that reports it is inside
`interp_profile_dump_atexit()`, which begins

```c
if (!HostGetenv("PHASE_MS")) return;
```

so **`SNESRECOMP_COUNT_PC` alone prints nothing at all**, silently, and the run
looks like a clean no-op. With `SNESRECOMP_PHASE_MS=1` added it reports:

```
[count] pc watched: 2 executions over 3700 frames = 0.0 per frame
```

This is the same shape as C-044 (`[interp_profile]`'s top-60 list printing
nothing without `SNESRECOMP_INTERP_MS_PROF=1`) — **a different knob, the same
mistake.** And `SNESRECOMP_COUNT_PC_FRAME`, documented at
`snesrecomp/runner/src/snes/interp816.c:196` as *"asks for the count to be
sampled and printed per frame"*, is **dead**: `s_interp_pc_frame` is declared at
`:200` and **never read anywhere in the tree**.

## 7. What this does NOT establish

- **Not a cause for the freeze.** `$03:D2AA` closing the gate is *where control
  goes*, not *why the city does not simulate*. The reference build also stops
  ticking productively, and the same `$0012` mechanism is **OPEN** there.
- **Not why `$03:D2A7`/`$03:D2AA` run at all.** The routine reached `$03:D299`
  with `LDA $14` / `BPL $03:D287` — i.e. it branches backwards unless bit 7 of
  `$0014` is set. **Why bit 7 of `$0014` is set at f3271 and not before is OPEN**
  and is the next thing to measure on this boundary.
- **Not the full entry graph of bank `$03`.** `$03:D287`–`$03:D29B` ran 2 311
  times while `$00:8056` ran **once**, so bank `$03` is re-entered by something
  other than `$00:8056` in 2 310 of those cases. **OPEN.**
- **Not the f108 write.** `$7F:0012 := $E0` from bank `$05` is one of the three
  writes and is not accounted for here; `$7F:0012` and `$00:0012` are the same
  physical byte, so what it did to the gate is **OPEN**.
- **Distinct-PC counts only.** Step counts are wall-clock dependent (C-049). The
  execution counts in §2 are counts of *distinct execution events at one PC*, so
  they are safe; no step count is used as a claim anywhere above.
