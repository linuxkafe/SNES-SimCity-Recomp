# T100 — does `$03:8026` run past f3857? No. And the date is frozen because *nothing writes it*

**Deck-native, 2026-10-02, `02bc55f`.** One ticket, two runs, no new source
code. Everything below was produced on `steamdeck` against a ROM whose md5 is
`23715fc7ef700b3999384d5be20f4db5`, with the environment caveat that travels
with every Deck number in this tree (503 of the 504 `/usr/include` paths
`pacman -Ql glibc` claims are absent from disk; the binary was compiled natively
against a hand-assembled prefix at `/home/deck/sysroot`).

## The machine and the runs

Deck `steamdeck`, gcc 15.1.1, cmake 4.0.3, Zen 2, 8 threads, Release, tier
`build-instr` (`-DSNESRECOMP_INTERP_PROFILE=1` on **both** `CMAKE_C_FLAGS` and
`CMAKE_CXX_FLAGS`). Tree rsynced from `02bc55f`; `cmake --build build-instr`
reported `[100%] Built target SimCitySNESRecomp` with nothing to rebuild, the
source commits since that binary's 16:04 stamp being documentation only.

Both runs: `scripts/d_city.script`, headless (`SDL_VIDEODRIVER=dummy
SDL_AUDIODRIVER=dummy`), logs to `/dev/shm`, foreground of a live ssh session.

## 1. F1 does not fire — the counter prints

The falsifier fixed in T100 before the run was F1: *the counter prints nothing
even with `PHASE_MS=1`*. It did not fire. A 200-frame smoke run was run first
for exactly this reason, at a cost of 10.7 s:

```
[host +10.739s] exit: RUN_FRAMES reached after 200 frames
[count] pc watched: 0 executions over 200 frames = 0.0 per frame
```

Trap 7 (`COUNT_PC` prints nothing without `PHASE_MS`) is real and was worked
around as documented. **Trap 8 is now refuted as a blocker**: with `PHASE_MS=1`
the instrument works, on this machine, first try.

## 2. `$03:8026` executes **zero** times over 0–6000 — and C-041b's objection is cured

```
$ SNESRECOMP_COUNT_PC=038026 SNESRECOMP_PHASE_MS=1 ...
[count] pc watched: 0 executions over 6000 frames = 0.0 per frame
```

`$03:8026`, ROM file `0x18026` = `EE 51 0B` = `INC.w $0B51` (verified against the
user's ROM on the host — machine-independent).

C-041b's caveat was that the f0–f3700 window **contains no frame in which the
reference build would have executed the tick even once**, so the zero it found
could not have been a finding. That objection is now answered rather than
argued: the reference's first tick is at **f3857** and its cadence is
+152/+253/+140/+243 = **197 frames per tick**, which puts **12 ticks inside
f0–6000** (f3857, 4009, 4262, 4402, 4554, 4807, 4947, 5190, 5342, 5595, 5735,
5978).

> **The tick instruction executes zero times in a window that contains twelve of
> its own.** That is a different kind of statement from C-041's, and it is the
> first one in this project that could have come out the other way.

**MEASURED, Deck-native.** `C-041b` is resolved in the direction that supports
the narrow reading; `C-041` stands.

## 3. The date is frozen because **nothing writes it** — 0 writes in 2 741 frames

The second run watched the whole clock block `$0B51`–`$0B5F`, not just the tick
counter. **66 byte-writes in 6 000 frames, and not one of them after f3259.**

| frames | writes | what it is |
|---|---|---|
| f0 | 15 | initialisation sweep, all `=00`, `IPC=$008023` |
| f108 | 15 | a **garbage-fill**: 15 *distinct* byte values, descending address order, `A` decrementing `74AE`→`74A0` |
| f563 | 2 | bank `$03`, `IPC=$0599FA`, `A=FFFF` |
| f581 | 2 | bank `$03`, `IPC=$059A4D`, `A=0081` |
| f582 | 15 | second zeroing sweep, all `=00` |
| f1205–f1685 | 10 | **a 96-frame periodic updater** (§5) |
| f2333 | 1 | one more, `A=4F81` |
| **f3259** | **6** | **the city-state write** (§4) |
| **f3260–f5999** | **0** | **nothing** |

```
$ wc -l < /dev/shm/wlog-clock.log
66
$ awk '$1 ~ /^f[3-9]/ && $1+0>3259' /dev/shm/wlog-clock.log | wc -l
0
```

This is strictly stronger than the project's standing claim, which was *"34 WRAM
bytes change across 2 599 frames"* — a statement about a *diff*. **This is a
statement about the writer**: the date field is not being rewritten with the
same value; **nothing writes it at all for 2 741 frames.** It is the first
mechanism-level measurement of the freeze in this project, and it does not name
a cause.

## 4. 1900/January is *written*, once, by a hardcoded initialiser

The six writes at f3259, with the ROM decoded from the user's image:

```
$03:C63F  A9 6C 07     LDA #$076C      ; logged A=076C  -> $0B53,$0B54 = 6C 07
$03:C642  8D 53 0B     STA $0B53       ; year
$03:C646  A9 01 00     LDA #$0001      ; logged A=0001  -> $0B55,$0B56 = 01 00
$03:C649  8D 55 0B     STA $0B55       ; month
...
$03:C77E  9C 51 0B     STZ.w $0B51     ; logged A=0007  -> $0B51,$0B52 = 00 00
```

The logged `A` values match the literals in the ROM exactly, and `$03:C642` and
`$03:C648` are the next-PCs of the two `LDA`s, which is what this host's
interpreter reports. **So the date is not a default nobody overwrote — the city
setup writes `1900 / January` at f3259, and nothing ever writes it again.**

**Two consequences, and the second is the interesting one.**

1. **`$03:C77E STZ.w $0B51` executes in our build at f3259.** That is the *same
   instruction and the same register state* the reference build's write-watch
   logged when it zeroed `$0B51` (`A=$0007 D=$0000 X=$003C S=1FF6` — ours reads
   `A=0007 X=003C S=1FF6`). **Our build reaches the writer neighbourhood the
   reference reaches.** It reaches the `STZ` and not the `INC`.
2. **f3259 is the frame the AOT histogram already flagged** and could not
   explain: `docs/measurements/2026-10-02-deck-aot-histogram.md` §5 records three
   unexplained AOT block entries at `$03C42A`/`$03C430`/`$03C463` in f3259, 11
   frames before the f3270 burst. It is now known that f3259 is the frame in
   which **this build creates and clears the city state**. That does not explain
   the three entries; it names the event they share a frame with. **OPEN.**

## 5. A 96-frame periodic updater in bank `$03` runs six times and stops

Also inside the clock block, and not previously known:

```
$03:D947  99 5C 0B     STA $0B5C,X     ; writes the next byte of the $0B5C-$0B5F run
$03:D94A  C8           INY
$03:D94B  8C 5B 0B     STY $0B5B       ; the counter
$03:D94E  64 50        STZ $50
$03:D950  60           RTS
```

| frame | writes | `$0B5B` becomes |
|---|---|---|
| f1205 | `$0B5C = 01` | 1 |
| f1301 | `$0B5D = 01` | 2 |
| f1397 | `$0B5E = 01` | 3 |
| f1493 | `$0B5F = 01` | 4 |
| f1589 | — | 5 |
| f1685 | — | 6 |
| f1771 … f6000 | **nothing** | — |
| f2333 | one lone write, `A=4F81` | 5 |

**Exactly +96 frames, six times, then silence.** Something in bank `$03` is
being updated on a 96-frame period — 1.6 s at 60 fps — for ten seconds of game
time and then stops. **This is a second silent boundary and it is OPEN. No cause
is claimed and none is implied**: it may be the same fault as the f3271 gate, or
an unrelated one, and this page cannot tell. It is recorded because a reader
scanning only the date fields would never see it.

## 6. R-034's sweep reproduces in our build, and the loop is now named

R-034 retracted a "fourth writer of `$0B51`" at `$00:8023` (`95 00`, read as a
one-byte-operand `STA dp,x`) on the evidence that the frame-0 writes covered the
watched span exactly, 256 bytes for a 256-byte range. **Our build shows the same
thing at the same frame and the same PC field**, and the loop can now be named
from ROM:

```
$00:8022  A9 00        LDA #$0000
$00:8024  95 00        STA dp          <-- block clear: store A at dp+X
$00:8026  E8           INX
$00:8028  88           DEY
$00:802A  D0 FA        BNE $8026
```

Logged at f0 with `IPC=$008023`, `X=$0B51`, `Y=$14AF` — X is the **target
address** and Y the **descending counter**, which is what a `STA dp / INX / DEY
/ BNE` clear looks like from the outside. `$00:8023` is the operand byte of the
`LDA` that loads the value being cleared with, and is not an instruction start
on either reading. The f108 and f582 events are the same shape parked at
`$05:9304` and `$00:94CC` (`$00:94CA` = `9F 00 02 7F` / `E8` / `88` — the same
`STA abs,X / INX / DEY` idiom).

**This is independent, Deck-native, on-our-side corroboration of R-034, from a
different instrument (a 16-bit bus write watch, not a PC census) on a different
machine.** Three of the fifteen bytes at f108 are non-zero garbage
(`0C AD 12 64 F9 AB …`), which is what distinguishes that event from a clear.

## 7. A PC-attribution convention that must NOT be carried across machines

The peer write-watch logs `cpu.pc`, which **that core sets to the next PC**. Our
host logs `g_interp_wlog_pc24`, and for every real instruction in §4 and §5 the
ROM decode matches at the **current** instruction's PC (`$03:C642` is the next
PC of the `LDA` at `$03:C63F`; `$03:D947` and `$03:D94B` are the two
instructions themselves). **Same log field name, opposite convention, different
machine** — the exact shape of CONF-8 and of R-034's "the logged next-PC does
not match its length", which was one of the three grounds R-034 was refuted on.

For the three sweep events the attribution matches **neither** convention
(`$008023` is not an instruction start and is not the next PC of any
instruction). That is consistent with the sweep reading and is reported as
*unattributed*, not as a fourth writer.

## 8. The fork T100 opened, closed: the tick *routine* does not run either

T100 counted **one PC**. That leaves a real fork: either the routine containing
it never runs, or it runs and one instruction inside it is missing. Both are
consistent with "0 executions", and they are different faults. Asked by
**effects** rather than by an instruction, over **9 000 frames**, watching the
two fields the tick routine feeds — `$0B51` (the counter) and `$0DC7` (the
accumulated tax, which the routine adds to two instructions later) — plus their
neighbours:

```
$ env ... SNESRECOMP_RUN_FRAMES=9000 SNESRECOMP_PHASE_MS=1        SNESRECOMP_COUNT_PC=038026        SNESRECOMP_WLOG_ADDR="0DC0:0DD0:/dev/shm/wlog-tax.log"        SNESRECOMP_WLOG_STATE=1 timeout 780 build-instr/SimCitySNESRecomp        --script "$PWD/scripts/d_city.script" "/home/deck/rom/SimCity (USA).sfc"
[host +298.394s] exit: RUN_FRAMES reached after 9000 frames
[count] pc watched: 0 executions over 9000 frames = 0.0 per frame
```

**61 writes to `$0DC0`–`$0DD0` in 9 000 frames, in four events:**

| frames | writes | what |
|---|---|---|
| f0 | 17 | zero-fill sweep, `IPC=$008023` |
| f108 | 17 | garbage-fill sweep, 17 distinct values |
| f582 | 17 | zero-fill sweep, `IPC=$0094CC` |
| **f3259** | **10** | **the city-state initialiser**, bank `$03` |
| **f3260–f8999** | **0** | **nothing. 5 741 frames.** |

```
$ wc -l < /dev/shm/wlog-tax.log
61
$ awk '$1+0>600' /dev/shm/wlog-tax.log | wc -l
0
```

`$0DC7` — the accumulated tax — is written exactly twice in 9 000 frames: once by
the f108 garbage sweep and once by the f3259 initialiser, as `00`. **It is never
accumulated into.** The tick routine's two nearest effects on WRAM both go
unwritten after the city is created.

**So the fork resolves to the first branch: the routine does not run.** Not "the
increment is missing" — the routine. And the count is still zero at 9 000 frames,
which extends §2's bound from f6000 to f9000.

### f3259 is one "new city" routine, and it is the only writer

The ten f3259 writes decode straight out of the ROM, and they are all part of a
single initialiser:

```
$03:C709  A9 07 00     LDA #$0007      -> $0DC5 = 07   (the per-tick tax amount)
$03:C70C  8D C5 0D     STA $0DC5
$03:C732  9C C7 0D     STZ $0DC7       (accumulated tax = 0)
$03:C70F  9C 8B 0B     STZ $0B8B
$03:C7B9  9C C3 0D     STZ $0DC3   ... $03:C7E3  9C CB 0D  STZ $0DCB
```

together with §4's `$03:C63F` (date = 1900/January) and `$03:C77E`
(`STZ.w $0B51`). **`A = 0007` and `A = 03E8` (= 1000) both appear in the logged
register state**, and `$0DC5 = 07` is exactly the "+7 per tick" the reference
build's trace attributes to this field.

> **The city-state block is written once, at f3259, by a creation routine, and
> never written again.** Not the date rewritten with the same value; not the tick
> counter failing to change; the whole block, initialised and abandoned.

**This is where the evidence now points, and it is not a cause.** It says what
does not write the city state. It does not say which code would have written it,
and this census — like every other instrument in this project — is a census of
*effects*. The gate at f3271 remains measured (`$03:D2AA` closes `$0012` and
`$00:804D` is never executed again), the bank-`$03` death at f3271 remains
measured, and **neither has been shown to be why the block is abandoned.**

## What this page does NOT establish

- **No cause for the city not simulating.** C-006 is unchanged and OPEN. This
  page says *nothing writes the date field after f3259*; it does not say why,
  and the writer census cannot see which code would have written it.
- **Nothing about `$0DC7`, `$0CE7`, `$0DAD`** or any other tick field — the watch
  covered `$0B51`–`$0B5F` only.
- **Nothing past f6000 for the clock block, f9000 for the tax block.** Both
  bounds are in the claims and stay in them. §8's 9 000-frame run watched
  `$0DC0`–`$0DD0` only; §3's 6 000-frame run watched `$0B51`–`$0B5F` only.
- **Nothing about the reference build's 12 ticks in this window.** They come
  from the T093 cadence, measured on the peer, and are used here **only** to
  establish that this window is one in which the tick *could* have appeared.
- **The f3259 AOT entries are still unexplained.** §4 names the frame they share
  with; it does not account for them.
- **The 96-frame boundary is OPEN** and is not connected to the f3271 gate by
  any measurement. Two silent boundaries 1 586 frames apart are not a causal
  chain, and this page does not offer one.
