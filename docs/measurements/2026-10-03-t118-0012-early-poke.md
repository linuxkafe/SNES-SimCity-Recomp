## 2. THE POKE MECHANISM — confirmed from source

`host_main.c:928-931`:
```c
if (e->mask & 0x40000000) {
    if (e->poke_bytes && e->poke_count > 0 &&
        e->poke_addr + (uint32)e->poke_count <= 0x20000u)
      memcpy(g_ram + e->poke_addr, e->poke_bytes, (size_t)e->poke_count);
    return 0;
}
```
Writes directly to `g_ram` (WRAM). Address is 16-bit WRAM offset (no bank prefix needed for `$0012`).

**Frame timing model** (`TickScript`, lines 899-969):
- Each entry: `wait_frames` (phase 1 countdown) → `hold_frames` (phase 0, action applied)
- `poke` defaults to `hold_frames = 1`
- After hold ends, next entry's `wait_frames` begins counting

**Script frame accounting** (from `scripts/d_city.script`):
- Total consumed before city live: 3224 frames
- Last entry [23] `mouseclick right`: fires f3218, ends f3224
- City appears at ~f3378 (154 frames after bank `$03` dies at f3271)

**My poke insertion point:** After entry [18] (`press down` at f2822..f2827), add `wait 173` + `poke 0012 01`:
- Entry [18] ends f2827
- `wait 173`: pending_wait=173
- `poke 0012 01`: fires at f2827+173 = **f3000** ✓
- Entry [19] fires at f3091 instead of f2917 (shift +174 frames)
- Subsequent entries shift by ~174 frames

The shift is documented. The city creation path is deterministic and frame-indexed; the game does not depend on absolute input timing.

## 5. INSTRUMENT LIMITATIONS — stated, not glossed

| instrument | sees | blind to |
|---|---|---|
| `SNESRECOMP_WLOG_ADDR` | both engines (`cpu_write8/16`) | DMA/HDMA writes (do not pass through `cpu_write8/16`) |
| `SNESRECOMP_INTERP_DUMP_BANK` | interpreter-only PCs | AOT executions (C-039c) |
| `SNESRECOMP_AOTBLK` | AOT block entries | Only if `SNESRECOMP_TRACE=1` is set AND `build-tr` is used |
| `SNESRECOMP_CYC_WATCH` | fetched opcode byte | AOT (`interp_bridge.c:2034`) |
| `SNESRECOMP_COUNT_PC` | one PC, interpreter tier | Other PCs; needs `0x` prefix (CONF-15) |
| `SNESRECOMP_INTERP_PROFILE_START/END` | frame window filter | N/A |

**CRITICAL:** `build-instr` does NOT have `SNESRECOMP_TRACE=1`. So `AOTBLK` will be a no-op in `build-instr`. To see AOT execution, I need `build-tr`. **This means `INTERP_DUMP_BANK=03` only sees interpreter-tier bank `$03` execution. If bank `$03` re-enters via AOT, `INTERP_DUMP_BANK` will show zero — a false negative.**

**To properly test AOT re-entry, I need to run with `build-tr` (trace tier) OR accept that `INTERP_DUMP_BANK` is the best we can do from `build-instr` and note the limitation.**

Actually, re-reading `cpu_trace.c:1234-1251`:
```c
void cpu_trace_block(CpuState *cpu, uint32_t pc24) {
    /* AOT block-charge probe ... env SNESRECOMP_AOTBLK="lo-hi" (frame window). */
    ...
    if (ab_lo >= 0 && snes_frame_counter >= ab_lo &&
        snes_frame_counter <= ab_hi)
        fprintf(stderr, "[aotblk] f=%d pc=$%06X master=%llu\n", ...);
}
```

This is inside `cpu_trace_block()`, which is called from the AOT path. Without `SNESRECOMP_TRACE=1`, this function may not be called at all, or may be a no-op. Let me check.

Actually, `cpu_trace_block` is defined in `cpu_trace.c` which is only compiled when `SNESRECOMP_TRACE_BUILD=ON`. The `build-instr` tier does NOT have trace build. So `[aotblk]` lines will not appear in `build-instr` output.

**Implication:** With `build-instr`, I can only measure interpreter-tier bank `$03` activity. If bank `$03` re-enters via AOT (which is possible — many bank `$03` routines are `aot_eligible`), `INTERP_DUMP_BANK=03` will show 0 even if the bank is executing.

**To fully test, I need `build-tr`.** But `build-tr` is slower (trace overhead). Let me plan for both tiers.
