## 1. What was tested

The peer latches `$0012` at f2998 and its bank `$03` re-enters at f3068 (70 frames later). Ours latches at f3271 and bank `$03` never re-enters. **T112 proved `$0012`'s *value* is not the gate — the peer runs with it set. This experiment tested whether its *timing* is causal.**

**Hypothesis:** If `$0012` is forced to `1` at ~f3000 in our build, bank `$03` will re-enter and `$0B51` will increment.

**Null hypothesis:** Early latching changes nothing. The divergence lies elsewhere.

## 5. Verdict and interpretation

### Verdict 2 confirmed

**The latch timing is NOT the gate.** Forcing `$0012 = 1` at f3085 (186 frames early) did not cause bank `$03` to re-enter. `$0B51` stayed 0 in both runs.

**R-046 is now confirmed twice:**
1. First: the peer comparison (T112) — `$0012=1` from f2998 in the peer, bank `$03` keeps running. Wait, this actually SUPPORTS the timing hypothesis... Let me re-read.

Actually, hold on. In the peer, `$0012` is set at f2998 and bank `$03` keeps running. In ours, if we set it early at f3085, bank `$03` still does NOT re-enter. This means:

- The peer's early `$0012` latch is **correlated with** bank `$03` re-entry, but not **causal** — the peer has something else going on that ours doesn't.
- The early poke in ours proves that `$0012` timing alone is not sufficient.

**What this means:** the divergence between the builds is NOT in the `$0012` latch. It must be in something else that differs between the builds and that enables bank `$03` re-entry in the peer. Possible candidates:
- Stack state (`S` is never restored, `S=1FFA` per T114)
- NMI delivery timing
- `$00B1` bit 7 restore timing
- Some WRAM location that the city-creation phase touches differently
- AOT vs interpreter tier discrepancy in bank `$03` code

## 6. Secondary question — what occupies f2998–f3271 in ours

The `$0014` scheduler trace shows the same 12 milestones in both builds. The only difference is frame numbers. In the peer, milestones `$08`–`$00` take f2838–f2997 (159 frames). In ours, they take f2636–f3270 (634 frames).

**The 475-frame difference is in the scheduler execution time.** The peer's scheduler runs ~475 frames faster in the tail (milestones `$08`–`$16`). This is NOT due to different code — the same 12 milestones, same writers, same values — but due to **different execution speed**, likely caused by a difference in the per-frame workload (more interpreted opcodes per frame in ours, taking more wall-clock time).

**This is a symptom, not a cause.** The scheduler is the same code; it just takes longer to run in ours. The 273-frame gap in latch timing is the *result* of this speed difference, not an independent gate.

**What about the 70 frames between peer's `$0012` latch (f2998) and bank `$03` re-entry (f3068)?** This gap is NOT explained by the timing difference. It is the time between the scheduler exiting and some OTHER code re-entering bank `$03`. **This code is still NOT IDENTIFIED.** It is the single next measurement.
